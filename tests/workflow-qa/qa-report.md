## Known gaps

1. **External failure isn't handled.** Neither Gmail node routes a failure anywhere — no logging, no alert. This is a real gap in the workflow as built, not a QA artifact. Fixing it is a separate, human-approved change to `automation-builder`'s output; this skill does not edit the workflow itself.
2. **Approver identity isn't logged.** `execution-plan.json`'s `outputs` calls for logging "who approved it," but `Log: Approved & Sent` only writes a generic notes string, not an approver identifier.
3. **`test_workflow`'s auto-pin claim doesn't hold for credential-less nodes.** The tool description says credentialed nodes are automatically pinned/simulated. In practice, `Send Summary To Customer` — which has *no* credential attached at all, not even a placeholder reference — attempted real execution and errored (`Node does not have any credentials set`) until pin data was explicitly supplied for it. `fixtures/happy-path.json` has been corrected to include this pin. Any future live test touching a Gmail/OpenAI node must pin it explicitly.
4. **Live QA runs left real rows in the production Data Table.** Executions 9–12 wrote rows (ids 5–8, `job_id`s `QA-TEST-HAPPY-01`/`MISSING-01`/`AIFAIL-01`/`APPROVAL-01`) into the live "LordGen Estimate Summary Log" table. These are clearly tagged but should be deleted from the n8n UI before a judge-facing demo — no MCP tool exists to delete Data Table rows.
5. **Duplicate execution is intentionally never live-tested.** `test_workflow` would write an untrackable row with no MCP tool available to delete it, and proving the "skip" behavior specifically requires a row to already exist. Static confirmation (structural + now schema-level via `get_node_types`) is as strong as this skill's own rules allow here.
