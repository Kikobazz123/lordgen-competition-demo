## Fixes applied (2026-08-19)

1. **External failure routing** (was gap #1): added `onError: continueErrorOutput` to both Gmail nodes, two new `Log: Delivery Failed (...)` dataTable-insert nodes (one per failure point — approval-request send vs. customer send, since they need different status/notes text and occur at different points in the flow), and a shared `End (Delivery Failed)` terminal. A send failure is now logged instead of silently lost.
2. **Approver identity logging** (was gap #2): added an `approved_by` column to the live Data Table (`add_data_table_column`) and populated it in `Log: Approved & Sent` and `Log: Delivery Failed (Customer Send)` via `={{ $node['Request Dispatcher Approval'].parameter['sendTo'] }}` — a dynamic reference to the approval-request recipient, not a hardcoded copy of the (private, not-committed) dispatcher address. **Important honesty caveat, confirmed by developer decision:** `get_node_types` shows n8n's Gmail `sendAndWait` (approval responseType) output schema is `{ data?: { approved?: boolean } }` — there is no approver-identity field at all; the approval link requires no login. `approved_by` therefore records *who the approval request was addressed to*, not a cryptographically verified identity of whoever clicked — the log's `notes` field says this explicitly so the record is never overclaimed as more than it is.

Both fixes were applied via `update_workflow` (13 atomic operations) and verified: structurally via `get_workflow_details` (new nodes/connections/`onError` settings all present as designed), and functionally via a fresh live `test_workflow` happy-path run (execution 13) confirming `approved_by` resolves to the real address and nothing in the four touched log nodes regressed.

## Known gaps

3. **`test_workflow`'s auto-pin claim doesn't hold for credential-less nodes.** The tool description says credentialed nodes are automatically pinned/simulated. In practice, `Send Summary To Customer` — which has *no* credential attached at all, not even a placeholder reference — attempted real execution and errored (`Node does not have any credentials set`) until pin data was explicitly supplied for it. `fixtures/happy-path.json` has been corrected to include this pin. Any future live test touching a Gmail/OpenAI node must pin it explicitly.
4. **Live QA runs have left real rows in the production Data Table.** Executions 9–13 wrote rows (ids 5–9, `job_id`s `QA-TEST-HAPPY-01`/`MISSING-01`/`AIFAIL-01`/`APPROVAL-01`/`REGRESSION-01`) into the live "LordGen Estimate Summary Log" table. These are clearly tagged but should be deleted from the n8n UI before a judge-facing demo — no MCP tool exists to delete Data Table rows.
5. **Duplicate execution is intentionally never live-tested.** `test_workflow` would write an untrackable row with no MCP tool available to delete it, and proving the "skip" behavior specifically requires a row to already exist. Static confirmation (structural + now schema-level via `get_node_types`) is as strong as this skill's own rules allow here.
6. **External failure remains static-only to verify** (see Results table) — this is an inherent limitation of pin-data testing against credentialed nodes, not something fixable within `workflow-qa`'s own rules.
